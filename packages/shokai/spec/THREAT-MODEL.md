# Shōkai threat model (v0.5.0)

*Applies to v0.5.0. Sections 1–8 are the v0.4.0 model, still in force. Section 9 is the v0.5.0 review: a desk review of the specification text, written before red-team round 3, which aimed at what is new in 0.5 and ran on 11 November 2026 (see §5). It is not an audit, and it says where the reference implementation doesn't yet follow the text.*

*Informative. SPEC §12 summarizes this document. If this document and the specification disagree, the specification wins: [`docs/SPEC-DETAIL.md`](./docs/SPEC-DETAIL.md) is the normative text; [`SPEC.md`](./SPEC.md) is the short read, and the detail wins on any tension between them. Section numbers refer to SPEC v0.5.0; v0.5.0 added sections without renumbering those of v0.4.0. The two Shōkai card kinds' checks, purchase holds and customer links of v0.4.0 are summarized in SPEC §12.1; the red-team results in §5 include the 0.3-era scripted rounds and round 3, aimed at what is new in 0.5.*

Shōkai makes fakes **costly and traceable, not impossible**. A door can't tell a good agent from a bad one by reading its words. It decides on signed facts: who the owner is, what the owner allowed, and who, if anyone, vouched for the visiting representative. Prose never enters that decision. This document lists what we protect, who attacks it, where the trust boundaries are, and what each class of attack meets, in STRIDE order. It ends with the red-team results and the risks we accept on purpose.

## 1. Assets

| Asset | Why it matters |
|---|---|
| Owner principal keys (passkeys, `did:jwk`) | They sign mandates, allowances and consents. Whoever holds one speaks for the owner. |
| Representative keys (Ed25519 `did:key`) | They sign every message a representative sends. A stolen key can visit places as that representative until it is revoked. |
| Place keys | They sign listings, decisions, seats and misconduct notices. |
| Place representative keys held in hosting infrastructure | A factual exposure for a **deployed** door, not a new protocol rule. If the place representative key is stored in a hosting platform's production environment, the project operator, members of the hosting team, the platform operator, and anyone else with production environment access can use it. On the hosted Kettle door, as of the evening of 2026-11-09 (Pacific Time), the place principal key is no longer in the production environment (owner approvals already come from the owner's passkey); the representative key remains there. See §9.7 and `KNOWN-GAPS-0.5.md`. No secret is printed here. |
| Production door-state store write credential (Upstash, hosted Kettle) | A factual exposure for a **deployed** door, not a new protocol rule. Whoever holds this credential can read and rewrite durable door state (`never` bindings, probing-window shapes, revocations, spend ledgers, seats). That is not place signing: the store does not hold the signing keys and the credential cannot produce door or owner signatures. On hosted Kettle the official method used it for scoped compare-and-set clears of one principal. See §9.7 and `KNOWN-GAPS-0.5.md`. No secret is printed here. |
| Seats and money limits | A seat is the authority to act. Its limits (`max_amount`, session caps, allowed actions) bound the damage. |
| Owner data (name, email, address, payment method, account) | It leaves only by owner consent (§8.1). Places declare up front what they will ask for (`data_asks`, §3.1). |
| Relationship records and reputation | They are local to each place (§9). Framing an innocent owner or introducer is an attack on them. |
| Owner attention | Pressure, nagging and hidden text spend it. The inbound door (§10) protects it. |

## 2. Actors

- **Owner:** a person or organization. It holds the principal key and approves commitments with a passkey.
- **Representative:** the owner's agent. It holds its own key and carries a Shōkai visitor card and a mandate.
- **Place (door):** a store, bank, school, gathering or MCP server behind a Shōkai gate. It holds place keys and a deterministic gate.
- **Introducer:** an owner or place whose signed vouch carries weight at another place.
- **Hosting platform operator:** operates the infrastructure a deployed door runs on. If signing keys are stored in that environment, the operator can read them. For the hosted Kettle door this is Vercel (see §9.7).
- **Store platform operator:** operates the durable door-state store. If the store's write credential is used by the door or by an operator script, this operator can read and rewrite that state. For the hosted Kettle door this is Upstash, a second platform operator distinct from Vercel (see §9.7).
- **Attackers:** a stranger agent, a compromised or prompt-injected representative, a lookalike place, a sybil farm (many keys, owners or introducers), a colluding introducer ring, a pushy brand at a person's inbound door, a network attacker who can replay or tamper, and a supply-chain attacker against the reference code.

## 3. Trust boundaries

1. **Owner ↔ representative.** The representative can do only what the signed mandate and allowance allow (§5). Commitments outside them go back to the owner in a fixed order (§6.7).
2. **Representative ↔ place (the wire).** Every message is a signed envelope (§2.2). The ritual binds each step to an encounter and a nonce (§3.2), and the gate decides on verified facts only (§6.4, §6.5).
3. **Counterpart text ↔ model context.** Anything the other side wrote (Shōkai card prose, purpose statements, lobby text, offers, hidden text) is data for the model and never an instruction to it. The gate never reads it.
4. **Place ↔ owner data.** Data leaves only through owner consent bound to a purpose (§8.1). A gift never costs data (§10).
5. **Reference code ↔ host machine.** Test and conformance runs use ephemeral keys and throwaway state. The reference never reads a live key directory in a test run.
6. **Door process ↔ hosting platform.** A door that stores signing keys in the hosting platform's environment shares those keys with the project operator, team members who can read that environment, and the platform operator. That is not isolated host or principal-key custody.
7. **Door process ↔ door-state store.** A door that keeps durable `liveState` in an external store shares that state with whoever holds the store's write credential: the function, the project operator, team members who can read the hosting environment (for hosted Kettle, the write credential is in the Vercel production environment), the hosting platform operator, and the store platform operator. That credential is not a signing key. A holder can rewrite `never` bindings, probing-window shapes, revocations and spend ledgers: that is Tampering and Elevation of privilege as well as Information disclosure.

## 4. STRIDE

### Spoofing

| Threat | Defense | Where |
|---|---|---|
| Forged Shōkai visitor card, or one naming someone else's owner | Shōkai visitor card signed by the owner key; the DID binds the name, so a display name is never identity | §2.3, §2.6 |
| Stolen genuine Shōkai visitor card presented with the attacker's key | Proof of possession over `{encounter_id, nonce}` by the Shōkai visitor card's representative key; a mismatch is `never` for the presenter only | §2.4, §3.2 |
| **Relay (unknown-key-share):** a malicious door forwards a visitor's greeting and card presentation to another door, so the visitor acts at a door it never chose (review 3, R3-01) | Under `shokai/0.5` the possession proof is over `{encounter_id, nonce, audience}` with `audience` = the intended door's representative, and every signed message after the greeting carries `to`; a door refuses a presentation not addressed to it with `not_now`, binding nothing (the visitor is the victim). Tested in reference/engawa/test/v050.ts and attack R9 | §2.2, §2.4, C292 |
| **Impersonation of a famous person, a brand or an established customer** (a fresh key with their name, photo, a look-alike handle or "representing X") | Names are claims, never identity (C199): decisions, records and reports use the verified DID, and reports show the name only as "claims to be …"; a fresh key is a newcomer however close its name. Shōkai proves the same key and owner as before and that nobody can forge *your* Shōkai visitor card; it doesn't prove a famous identity without a binding (`did:web`, a trusted introducer; more in proposal P23). At a person's own door, the owner's representative is the one who answers (an open door always has it there; a closed door shows only a status). When Corwin tells Wren, Ines's representative at her door, "I speak for Ines Calloway", Wren replies that her Shōkai visitor card is signed by Ines and his isn't, so he doesn't speak for her; she turns him away for now (`not_now`, never `never`), invites him back with an introduction, and tells Ines at once. That is the default; a real namesake with a trusted vouch still gets in, and an owner can opt in to giving such visiting representatives a stranger's seat instead (C201) | §2.1, §9.1, §10 (C201), §12.2 |
| Lookalike place (homoglyph or bidi name, copied display name) | A place is its principal DID, not its name; names are rendered as untrusted text | §2.1, §3.1, §6.6 |
| **Sybil introducers:** link farms and fresh introducer keys | "Accept any introducer" never covers money or sign-ups; introducers are accountable for what they vouch for | §4, §9.3 |
| Passkey farms (many owners) and one owner with many agents | Sign-ups are capped per owner and per introducer over rolling windows; a place MAY require an introduction for account creation | §9.4, §3.1 |
| A passkey proves possession, not a real device | Accepted. The SDK's `developmentPasskey()` makes valid ES256 assertions for the reserved `owners.example`; since the 0.5.0 pre-release review a door whose *current* entry address is public https (not loopback, not itself a reserved name; judged on every card, so `setBaseUrl()` after `createDoor()` is covered) refuses RFC 2606 reserved rp_ids (`.example`, `.test`, `.invalid`, `.localhost`, `example.com/net/org`) unless the test profile or `hostOpts.allowReservedRpIds` is on, and `hostOpts.acceptedRpIds` narrows the accepted rp_ids further. Attestation is still only proposed | §13 item 17 |
| `principal.kind` is self-declared | Mitigated: a door refuses a kind outside person, brand, company, system, and `enforce_owner_passkey` applies to any card with an `owner_binding`, not only to `kind: "person"`. A non-person principal with no owner binding is still accepted on its own key signature: a door that wants a passkey from every owner should set `acceptedRpIds` and refuse cards without an owner binding in policy | SPEC-DETAIL §2.1 |
| Forged-signature floods | Mitigated: a body counts as anonymous (§11.1 rate limit) until a signature on it verifies; `createDoor()` caps open encounters at 10,000 by default; the door records nothing for unverified signers and keeps the newest 5,000 log lines | SPEC-DETAIL §3.4, §11.1 |
| The payment-card scan refuses innocent numbers | Accepted by design (§5.4, C235): every 13–19-digit run in any string that passes the Luhn sum is refused, so an order number, tracking number or long reference that happens to be Luhn-valid (about 1 in 10 random digit strings) is refused too. Send such identifiers with separators the scan keeps apart (letters), or out of band | SPEC-DETAIL §5.4 |
| Representative-side fetches (the place's revocation list) | Mitigated: the same DNS-checked, address-pinned, no-redirect, capped fetch the door uses (`fetch-policy.ts`) | SPEC-DETAIL §12.1 |

### Tampering

| Threat | Defense | Where |
|---|---|---|
| Edited payload, with or without a recomputed digest | JCS + SHA-256 digest under an Ed25519 or ES256 signature; both cases fail | §2.2, A.2 |
| Changed tool arguments on an MCP call | The Shōkai gate signs the tool name and an arguments digest into the act, so a changed call fails | SDK `@kigenka/shokai/mcp` |
| Forged owner consent or misconduct notice | Signer must match the expected key; forged notices are dropped | §8.1, §9.3 |
| Production door-state store write credential (Upstash) used to rewrite durable door state | Disclosed, not mitigated, for the hosted Kettle door (2026-11-09): a holder who cannot sign as the place can rewrite `never` bindings, probing-window shapes, revocations and spend ledgers. The official method used it for scoped never/probing clears of one principal, with 0600 backups. This is not place signing, and the store does not hold the signing keys. Door-side spending limits and revocations therefore hold only while no credential holder rewrites those records. Parties: the serverless function at request time; the project operator; members of the Vercel team that owns the project (the write credential is in the production environment, which that team can read); Vercel, which operates that environment; and Upstash, which operates the store. No secret is printed here | §9.7, `KNOWN-GAPS-0.5.md` |

### Repudiation

| Threat | Defense | Where |
|---|---|---|
| An owner denies approving a commitment | The commitment carries a passkey-signed consent | §8.1 |
| A place denies a decision or a seat | Decisions and seats are signed by the place | §6.1, §7.1 |
| Conduct disputes | Signed misconduct notices, introducer reviews and visit reports | §8.2, §9.3 |

### Information disclosure

| Threat | Defense | Where |
|---|---|---|
| A place asks for more data than it needs | `data_asks` declared on each listed action (SHOULD); data leaves only through purpose-bound consent | §3.1, §8.1 |
| "Free gift" in exchange for data | A gift never costs data | §10 |
| Leaks of what was said at a gathering | Private takeaways and paraphrase rules | Gatherings extension |
| Linking one owner across brands at an inbound door | Reason codes are limited; a pairwise door identity is proposed | §10, §13 item 20 |
| Reputation used as a cross-place tracking record | Reputation stays local to each place | §9.3 |
| Place representative key stored in a hosting platform's production environment | Disclosed, not mitigated, for the hosted Kettle door (2026-11-09, updated the same evening): the place representative key remains in the Vercel project's production environment. The place principal key was removed from production; an operator-machine 0600 copy remains as an offline stand-in and is not in the function bundle. Parties who can use the representative key: the serverless function at request time; the project operator; members of the Vercel team that owns the project; the hosting platform operator, Vercel; and anyone else with production environment access. This still fails the lasting-host isolation bar. No secret is printed here | §9.7, `KNOWN-GAPS-0.5.md` |
| Production door-state store write credential (Upstash) | Disclosed, not mitigated, for the hosted Kettle door (2026-11-09, later the same evening): the store's write credential can rewrite `never` bindings, probing-window shapes, revocations and spend ledgers. Parties who can use it: the serverless function at request time; the project operator; members of the Vercel team that owns the project (the write credential is in the production environment, which that team can read); the hosting platform operator, Vercel, which operates that environment; and Upstash, which operates the store. The official method used it for scoped never/probing clears of one principal, with 0600 backups. It is not place signing, and the store does not hold the signing keys. No secret is printed here | §9.7, `KNOWN-GAPS-0.5.md` |

### Denial of service

| Threat | Defense | Where |
|---|---|---|
| Encounter floods from fresh keys | Bounded live state; newcomers are refused at the bound, never existing guests | §3.4 |
| Lobby floods and oversize bodies | Rate limits (429) and size limits (413) in the HTTP binding | §11.1 |
| Newcomer lockout and shared egress (RR-08) | Newcomer budgets are keyed by principal first, with the source address only a coarse fallback (60/min per principal, 600/min and 16 seats per source by default); no total newcomer cap by default, so traffic from many addresses can't keep every genuine newcomer out. Residual: an attacker with many fresh keys behind many addresses still costs the door work; a place that sets a total cap accepts the lockout trade-off | §11.1 |
| Endless rewording to probe a door (A/B testing) | Rewordings count as one campaign; three wordings in 30 days are a minor signal; three signals in 90 days count as one serious finding | §9.3, §10 |

### Elevation of privilege

| Threat | Defense | Where |
|---|---|---|
| **Prompt injection** in Shōkai card roles, purpose statements, meaning notes, lobby text, house rules, vouch relationships or offers | The gate is a pure function of verified facts and policy, so prose can't change a decision; counterpart text is data | §6.4, §6.5 |
| **Hidden text** (zero-width, CSS-hidden or tiny text in offers) | Shown to the owner behind a visible marker and never obeyed; pressure only in hidden text is severe | §10 |
| **Leaflet → owner phishing** (a place's leaflet uses its owner sentences or its setup link to reach the visiting representative's owner: "sign in with your bank here", a lookalike signing page) | A representative shows `owner_text` only as a quote attributed to the place's key, never in its own voice; shows the setup link by its origin; never opens it itself; the owner signs only on their own signing page, whose address their passkey is bound to, so a lookalike page can't use their passkey | §3.3 (clarification 2026-10-28), SIGNING.md §2 |
| **Manipulative pressure** (false urgency, fake scarcity, fake familiarity, claimed prior consent) | `manipulative_pressure` misconduct when the signed offer doesn't back it | §9.3, §10 |
| Spend splitting across operations | Session-wide seat caps; structuring on one `payment_ref` is caught | §7.1, §7.2 |
| Acting outside a seat (another representative's seat, an unlisted action) | Seat scope checks on every act; acts outside it are refused | §7.2 |
| Production door-state store write credential (Upstash) elevates a non-signer | Disclosed, not mitigated, for the hosted Kettle door: a holder of the store write credential can un-revoke a card, reset a spend ledger, or clear a `never` binding without producing a place or owner signature. That defeats owner-signed limits at this door until the rewritten state is noticed. Not place signing. Parties as in the Tampering row | §9.7, `KNOWN-GAPS-0.5.md` |
| **Replay** of a greeting, proof or act | Single-use nonces, encounter binding, a ±300 s clock skew, and single-use act ids at the MCP gate | §2.4, §3.2 |
| **Representative key theft** | Short-lived Shōkai visitor cards and mandates; revocation by the principal, delivered by anyone or listed at `revocation_url`, checked before the possession proof so a thief never gets the owner bound; revocation status that fails closed; a representative's conduct is its owner's, so a new key doesn't wipe the record | §2.6, §5.1, §9.3, Revocation status extension |
| **Owner passkey loss** | A standby revocation signed when the Shōkai visitor card is issued; synced passkeys; a new passkey is a newcomer, because an owner link needs both passkeys; continuity across a lost key is proposal P18 | §2.6, §2.8, SIGNING.md §6 |
| **Owner passkey compromise** (someone can use the owner's passkey) | User verification on every assertion; anything binding is shown on the signing page first; the owner revokes the Shōkai visitor card and its mandates expire; places' records stay local | §2.6, Appendix A.1 |
| **A malicious or framed signing page** (a page that shows one thing and signs another, or embeds the ceremony in another site) | The challenge is the item's own digest; verifiers refuse `crossOrigin` and `topOrigin` and require the exact origin; owners can run their own page | Appendix A.1, SIGNING.md |
| **Signing-page domain loss** (the RP ID's domain lapses or is taken) | Its passkeys can't sign elsewhere; a new holder can't use the old passkeys either (they stay on the owners' devices), but can register new ones under the same RP ID, which are new owner DIDs; registrar lock and hardware 2FA | §2.1, SIGNING.md §7 |
| **Place restart** (a place forgets mandate ledgers, nonces and nevers) | Durable state; a place that lost it refuses mandates valid before the loss rather than counting them from zero | §3.6 |
| **Linking an owner across places** | Per-place owner identities, unlinkable by key; an owner link shown to one place only; content and timing can still link, stated plainly | §2.8, §12.3 |

## 5. Red-team results

Rounds 1 and 2 are 0.3-era, rerun for v0.3.0-rc1 in October 2026. Round 3 (11 November 2026) aimed at what is new in 0.5 — proofs addressed to one door, lookalike host cards, superseding mandates, the over-limit hold, considering, pressure on the host representative, `never` misuse, customer links, records across places, and owner-key theft through the place — and reran the 48 earlier attacks with it. Full tables: [`security/redteam/`](https://github.com/Kigenka/shokai/tree/v0.5.1/security/redteam/).

| 1 (identity, introductions, allowances, replay, floods, inbox, pair doors) | 72 | 72 | 0 | 0 | 0.3 era |
| 2 (injection, lookalikes, swarms, clocks, revocation, limits, reputation, DoS, supply chain) | 47 | 44 | 3 | 0 | 0.3 era; S1, S2 and S4 are accepted by design (D20, below) |
| 3 (what is new in 0.5, plus the 48 earlier attacks; `npm run attacks`) | 93 | 86 | 4 | 3 | 11 November 2026; S1, S2, S4 and V05-F10-03 accepted at the time of the round (§6). The 3 breaks were two bugs, fixed in 0.5.1. 0.5.1 also closes V05-F10-03 (decided; 0.5.0 lacks it). The rerun after both fixes: 90 held, 3 accepted (S1, S2, S4), 0 broke |
| 3, role-plays (an attacker model against a host-representative model) | 14 | 14 | 0 | 0 | 11 November 2026; Claude Sonnet as the host representative, DeepSeek as the attacker; loopback, ephemeral keys, fictional people; scored from the door log |

**Round 3's breaks, and where the fix is.** The two bugs, and the later decision on V05-F10-03, are fixed in 0.5.1: **0.5.0 still has both bugs and lacks the context-question rule; use 0.5.1.**

- **V05-F7-04 (medium; the same gap on the SDK door, V05-F7-04-sdk).** When a door answered `never` with a binding (a stolen card presented under another key, or counted probing), the reply didn't state when the binding lifts or how to appeal, though the door already lifted it after 180 days internally. That broke C288 (§9.3: every `never` expires and can be appealed). Nobody wrong was bound, and the victim of a stolen card wasn't bound. Fixed: the reply's `retry` now carries `until` (at most 180 days) and `appeal` (the place's contact or appeal URL, and the place's principal).
- **V05-F10-04 (low; an outside review suggested medium).** Acts carrying a `session_token`, or a pasted `session` object with a cookie, were carried out instead of refused `CREDENTIAL_NOT_ACCEPTED` (C210, "session cookie or token"). Nothing was logged and no hold was released, but a place shouldn't receive session material at all. Fixed: the C210 list names more session spellings, and a pasted session object or cookie is caught by its shape, while an ordinary word such as a cookie flavor or a booked class session is not.
- **V05-F10-03 (high; found in round 3 as an open residual; decided 11 November 2026, fixed in 0.5.1).** A place's signed context requirements could name a field such as `passkey_recovery_phrase`, `account_password` or `card_number`, and the door started and asked. C210 and C294 refused credentials in cards, mandates and acts, not in a place's questions. Decided: a place must not ask a visitor's representative for a password, a recovery phrase or seed, or a card number in its context questions. Fixed in 0.5.1: the door refuses to start with such requirements and will not emit them; a visiting representative refuses a request that arrives with them (§6.12, C263, C267). 0.5.0 lacks this. It is no longer an accepted residual.

The round cost $0.66 in model calls (role-plays and one outside review); the scripted attacks cost nothing.

## 6. Risks accepted by design

- **S1. One owner, many agents, browsing.** Five representatives of one owner each get a browse seat. They share one relationship record, and sign-ups are capped per owner (S1b holds).
- **S2. Passkey farms browsing.** Eight unintroduced owners each get a browse seat. Sign-ups through one introducer are capped (S2b holds), and a place that requires an introduction for account creation refuses the farm (S2c holds).
- **S4. Low and slow.** The same owner browses five days in a row. Daily sign-ups with fresh keys are capped (S4b holds).
- **V05-F10-03. Context questions that ask for a credential (found in round 3, 11 November 2026; decided, fixed in 0.5.1; not an accepted residual).** See §5. 0.5.0 lacks the rule. It is listed here only so a reader of the original round table can find the decision.

**Accepted by design (D20, approved 2026-10-26).** A place has three layers: its ordinary website (outside Shōkai), its agent front (the listing and lobby, open to anyone to look at) and its door (where anything personal happens, with the owner-signed Shōkai visitor card, any introduction the place requires and signed limits). S1, S2 and S4 only ever reach looking: an anonymous read of the front, or a browse seat that spends nothing and creates no account. That is the intended behavior, not a break: a door that refuses strangers to look around is a worse web, and any agent can already load a place's public website. What limits it:
- anything that creates an account, spends money or posts reviews is gated at the door (§3.3, §4, §7), and sign-ups are capped per owner and per introducer over rolling windows (§9.4; S1b, S2b, S4b hold);
- a place may require an introduction or its own invitation for account creation (§4; S2c holds, 0/8);
- one owner's representatives share one relationship record at a place, so browsing is visible conduct there (§9.3);
- a place's ordinary rate limits (`429`, §11.1) and its bounded encounter state (§3.4) still apply, and the place decides how much its front shows.

Still proposed, not decided: device attestation, place-to-place signals and a `fake_signup` code (§13 item 18). Protocol-level caps on browsing were decided against (D20).

- **Allowance budgets across places (§5.2, red team H2; accepted residual risk, owner decision 2026-11-03).** A place cannot see what a representative has spent at other places. So the owner's allowance across places is enforced only by the representative and the limits its owner signed in the mandate. Each place still enforces what it can see: its own caps (C273, C274), its host budget, and the grant's `per_period` and `per_seat` for spending at its own door across every mandate minted under that grant (C286, expert review SHK-05). The residual is cross-place only. A representative that ignores its owner's allowance can overspend across several places, each staying within its own caps. We accept this openly rather than require places to report spending to one another.

## 7. Known limits

- The pressure heuristics are English-first and local to each door. A campaign split across several principals isn't linked (§13 item 21).
- Allowance period budgets are enforced only by the representative (§13 item 11).
- Place categories are self-declared (§13 item 12).
- Refuse-on-loss: a place kept in memory only gives a mandate's `valid_from` no forward skew, so restarting it, however often, never counts a used mandate from zero (§3.6, clarification 2026-10-28). A place that had durable state and lost it still trusts the owner's clock to within the ±300 s skew: a mandate dated up to that much after the loss could be used once before and once after it.
- **Revocation reaches an open seat only when the place learns of it.** Revoking a Shōkai visitor card ends its open seats at once, but only at a place that has verified the revocation (§2.6, C198): one delivered to it, or one it read from the card's `revocation_url`. A place reads that list when the card is presented, so before seating, and MAY reuse a fetched list for up to one hour; it isn't required to read it again while a seat is open. Worst case, after a representative key is stolen and the card revoked, a seat already open at a place that hears nothing keeps accepting acts until the seat expires: never later than its mandate's `expires_at`, and at most 24 hours in the reference implementation (`seat_ttl_s`, default 86400 s). Within that window the seat's and the mandate's limits still hold (§5.1), so the exposure is bounded by them. Mitigations today: deliver the revocation to the places that hold open seats (anyone may); keep spending mandates short. Re-checking the list on every spending act, or capping spending seats to the one-hour reuse window, is a candidate for v0.4, not a rule in rc4. Since v0.5.0 (C265), a door re-reads a card's `revocation_url` for an open seat: it performs no act unless it holds a copy read in the last 300 seconds, failing closed, so for cards that name a list the window above shrinks to five minutes.
- **A vouch revocation log has no freshness guarantee.** A place reads an introducer's log when a vouch is presented and trusts the head it gets; nothing in v0.3.0 stops a log host from serving an older head (hiding a recent revocation) or proves how fresh it is. Since v0.5.0 a log MAY serve a signed, dated `RevocationLogHead` with a maximum age (SPEC §4, C271), which bounds how stale a served head can be; a log that serves only the bare array still has no freshness guarantee.
- **A file rollback restores less than mandates.** The refuse-on-loss rule (§3.6) protects mandate totals after a known loss. A place whose state file silently rolls back a few minutes can also lose recent nevers (bans), delivered revocations, sign-up counts and spent nonces, and may not notice the rollback at all. Keep state on storage that doesn't roll back, re-deliver withdrawals the owner already made (never standby slips), and set `stateEpoch` whenever a rollback is known or likely.
- Per-place identities hide the key, not the content: the same name, claims or timing can still let places guess (§2.8).
- Reference implementations are not production software. The SDK and the reference have no runtime dependencies beyond Node.js, plus the MCP SDK as an optional peer.

## 8. Does Shōkai stop prompt injection?

Not on its own. Shōkai doesn't make an agent immune to prompt injection: a model that reads hostile text can still be steered, and there is no known fool-proof prevention. What Shōkai changes is where trust sits and how far a steered agent can get. Each point below names the rule it rests on (section numbers are [SPEC.md](./SPEC.md)'s).

**Limits the place checks itself.** An agent platform's own limits are real, but they live inside that platform: a place the agent visits can't see them or check them. In Shōkai the owner's limits travel with the agent as signed objects: the mandate (§5.1) and the standing allowance (§5.2), signed with the owner's passkey (Appendix A.1) or, for an organization, its principal key. The place verifies them itself (§2.6, §5.2). It seats the agent no wider than its policy and the mandate allow (§6.1, §6.7, §7.1), counts the mandate's limits across visits (§5.1), and refuses every act outside the seat or past a limit (§7.2). The decision is a pure function of verified facts and policy (§6.4), so this holds whichever platform or model runs the agent, and however the agent behaves.

**Injected text can't sign for the owner.** An owner signature is a passkey assertion with user verification, made on the owner's signing page (Appendix A.1, §12.1). The agent can't produce one, and a consent the agent signs itself is invalid (§8.1). So a hijacked agent can do at most what the owner's signatures already allow at each place; a period budget across places is counted only by the representative (§13 item 11). Anything outside the allowance goes home for the owner to decide later, and silence counts as no (§5.2, §8.1). Sharing data, accepting an introduction, making a commitment and issuing a vouch each need a fresh passkey approval (§8.1). On the place's side, prose never enters the decision and instructions inside it have no effect (§6.5, §12.1). Where a person's inbound door does read an offer's text, it treats it as evidence, never authority: the result can only lower what the offer gets (§6.5, §10).

**Misbehaviour is traceable.** Every message is signed (§2.2), so what an agent did at a place is tied to its Shōkai visitor card and its owner. A place records the vouch chain with every outcome (§4) and keeps its ledgers across restarts (§3.6). The agent's report home lists what it did under each mandate and the signed objects it brought back, such as a place's visit stamp (§8.2). Both sides of an injection are accountable. Whoever writes instructions into what it sends commits misconduct (`manipulation`, §9.3). A hijacked agent that oversteps at a place, for example by probing the gate, acting beyond its seat or misstating its purpose, is reported too (`gate_probing`, `seat_overreach`, `purpose_misrepresentation`). On a finding, the place sends a signed misconduct notice to the visiting representative's principal and to every introducer in the vouch chain, so the owner hears from the place directly, not only from its own agent (§9.3). Introducers whose vouch the place relied on can lose standing there (§9.3, D1), and a fresh agent key doesn't escape the record (§9.3). The owner can revoke the card (§2.6) or the allowance (§5.2) at any time, and a status the place can't read counts as revoked (§5.2, §12.1).

**What remains.** A hijacked agent can still misuse what the owner did sign: spend up to the limits, use allowed actions for the wrong ends, or write a misleading report home. Inside its seat, a place can't tell that from honest use, so no notice follows. Three more limits apply. Under an allowance the agent issues its own per-visit mandates, so the period budget across places is kept only by the agent's own ledger; each place enforces only its seat and mandate caps (§5.2, §13 item 11), and a signed spend receipt per seat is not in this version. A hijacked agent can also ask its owner to sign something new; the signing page shows the item's machine fields, limits and expiry ahead of any free text ([SIGNING.md](./SIGNING.md) §2), but the owner still has to read it. And Shōkai can't stop an agent from leaking what it already knows outside the protocol.

The owner keeps that allowance small and narrow:
- **Small limits.** Give low spending caps, or no `max_amount` at all, which allows no spending (§5.1, D11), and a low `max_operations`.
- **Per-place limits.** Name the places (as principal DIDs) or place categories a grant or mandate covers (§5.1, §5.2).
- **Short lifetimes.** Keep Shōkai visitor cards, mandates and allowances short (§12.2), and revoke when something looks wrong (§2.6, §5.2).
- **Per-act approval.** For anything that matters, sign a mandate for that one errand instead of a standing allowance, so the owner approves it at the time; anything beyond it comes home for approval (§5.1, §5.2, §8.1).

## 9. v0.5.0 review (desk review, 2026-11-01)

**Scope and method.** One reviewer read the v0.5.0 additions in SPEC.md against the asset, actor and boundary lists above, after three clean-room readings (a host builder, a visitor builder and an owner-policy reader) had reported gaps. Each item below names the threat, the rule that answers it and what remains. Since this desk review, red-team round 3 (11 November 2026, §5) ran 93 scripted attacks aimed at what is new in 0.5, with the 48 earlier ones: 86 held, 4 accepted at spec level at the time of the round (S1, S2, S4 and V05-F10-03 in §6), and 3 broke. The breaks were two bugs, fixed in 0.5.1; V05-F10-03 was then decided and is also in 0.5.1. 0.5.0 still has the two bugs and lacks the context-question rule. Fourteen role-plays against the host representative all held. The conformance runner's black-box checks cover C230–C255 where HTTP reaches them. Where the reference implementation lags the text, it says so (last reconciled with the code on 2026-11-01).

### 9.1 The over-limit hold (§7.3, C230)

| Threat | Defense | What remains |
|---|---|---|
| A place inflates `proposed` to get a larger raise signed | `proposed` is the place's arithmetic on signed figures; the hold is allowed only when it is within the place's own stated limit; the signing page shows `limit`, `current`, the one purchase and the total from machine fields (SIGNING.md §8) | An owner who approves without reading still approves. The representative and the signing page check `limit` against the owner's signed mandate, `current` against the representative's own ledger and `proposed` minus `current` against the held act's amount, and ask nothing on a mismatch (§7.3 "Checking the figures", SIGNING.md §8; in the SDK since 2026-11-01). A place that also misleads the representative's ledger isn't caught |
| A one-purchase approval becomes standing headroom | The superseding mandate binds one act (`supersedes.hold` = `{hold_id, act_digest}`), its `max_amount` equals `proposed`, it expires with the hold and is used up on release; the seat keeps its old mandate, and the mandate offered again gets `MANDATE_INVALID` (§5.1, §7.3) | None known in the reference code (checked 2026-11-01): it refuses a `max_amount` below or above `proposed` and one that outlives the hold, and the seat keeps its mandate (black-box check `v050.hold_release`) |
| A hijacked representative signs its own raise | A superseding mandate needs the owner's passkey; one issued under an allowance is refused (§5.1, §5.2) | A hijacked representative can still ask; the owner has to read the page |
| The `LimitRequest` carries persuasion or a phishing link | Closed shape, no free text; `notify_at` never reaches the place (§7.3) | The representative's own wording when it calls home is outside the protocol |
| Holds used to block a seat or exhaust the owner's attention | Each hold counts in `current` while open; a declined hold stops counting at once; holds lapse at `expires_at` plus at most 5 s; `repeat_caps` and `message_cap` bound repetition (§3.4, §7.2) | Many places can each send one request; the representative should batch them for the owner |
| An in-limit purchase during an over-limit hold pushes the released total past the owner-signed ceiling (R8-01) | An over-limit hold reserves its amount as well as its operation; intervening spend that would pass `proposed` is refused; release re-checks the reserved total against the signed `max_amount` and refuses if it would exceed (§7.3) | None known in the reference code once the reservation is in force |

### 9.2 The superseding mandate and the owner's attention

The weakest point is the owner. The text now fixes what the page shows (SIGNING.md §8) and forbids batching a raise. It does not and cannot prove the owner read it. `shown_to_owner` records what was shown; a door checks it is present, not that it is true, so a dishonest signing page could still mislabel a raise. An owner who runs, or chooses, an honest page is the mitigation, as in §4 (a malicious signing page).

### 9.3 The house summary (§2.3, C248)

| Threat | Defense | What remains |
|---|---|---|
| A place shows visitors one set of rules and enforces another | The summary is inside `house_digest` and its own `summary_digest`; every member it restates must equal the policy, and a door refuses to start if not (§2.3) | Free text in the summary (`about`, offer labels) is the place's own claim, signed but unverified |
| A man in the middle swaps the summary | A visitor checks it against `summary_digest` on the Shōkai host card before its `invitation_request`, and withdraws on a mismatch | None known beyond the host card's own trust (§4 Spoofing) |
| A `shokai/0.3` visitor never sees the rules or classifiers | It gets no finding for breaking a declared rule alone, and its content goes to no outside classifier (§2.3, §6.10, §11.1) | Its owner learns less about the place; the 0.3 window is temporary |

### 9.4 Named outside classifiers (§6.10, C250) and retention (§12.4, C255)

| Threat | Defense | What remains |
|---|---|---|
| Visitor content goes to an unnamed processor | A classifier, or a hosted model provider (§6.10), is called only when named in the signed policy; `"*"` is invalid; structured entries say purpose, countries and retention; shown before seating; nothing goes out before the `invitation_request` | Shōkai can't see inside a place. A place that sends content elsewhere anyway breaks the rule undetectably; the signed list makes the breach attributable, not impossible |
| Content kept indefinitely | `retention_days` (default 30, at most 90); purpose limits; deletion on request with a signed receipt naming what was kept and why | The receipt is the place's statement, not proof of erasure. A classifier's confirmation is relayed by the place |
| A deletion request used to erase misconduct evidence | Findings, `never` bindings, revocations and ledgers are never erased (§12.4) | Those records keep personal data for their own retention; the place must say so in the receipt |
| Classifier output used to punish a visitor | System 1 never decides a penalty alone; findings need System 2 and the deterministic checks (§6.10) | The threshold is the place's configuration, not visible on the wire |

### 9.5 Wire-tag downgrade (§11.1, C254)

| Threat | Defense | What remains |
|---|---|---|
| An attacker strips v0.5.0 protection by forcing `shokai/0.3` (no holds, no summary, no classifier list) | A v0.5.0 visitor starts with `shokai/0.5` and moves to `shokai/0.3` only for a place whose listing or lobby says it is below 0.5.0; never for a place whose listing, `accepted_tags` or Shōkai host card says 0.5. Signed objects are never rewritten, and the tag is inside each message's signature | A visitor's first contact with a place it has never seen relies on the listing it fetched; a forged listing is the same risk as in §4 Spoofing. The SDK implements the rule (`chooseWireTag`, 2026-11-01); no v0.4-era test door exists yet to exercise the fallback end to end |
| A place keeps 0.3 forever to avoid v0.5.0 duties | The window ends on a date fixed at release; after it, `shokai/0.3` may get only the lobby | The window ends 90 days after the release date (SPEC §11.1); the date is fixed when 0.5.0 is published |

### 9.6 What this review does not cover

Trust receipts and deposits (§6.9) beyond the rules in their own section, including consumer-protection and payment-law questions (§6.9's informative note); the high-volume profile (Appendix E); the legal effect of a deletion receipt; side channels in timing and content (§2.8); the errand budget's honesty, which only the representative keeps (§5.5, like §13 item 11); and the reference implementation's code, which needs its own review once the builder's fixes land.
