# What the MCP binding (SPEC §11.3) uses from MCP revision 2026-07-28 (informative)

*Informative notes for [SPEC.md §11.3](../SPEC.md#113-the-mcp-binding-c179c182), written in our own words so an implementer reading the bundle offline knows which parts of the Model Context Protocol the binding relies on. The MCP specification is the normative source: <https://modelcontextprotocol.io/specification/2026-07-28> (its changelog: <https://modelcontextprotocol.io/specification/2026-07-28/changelog>). Checked on 2026-10-27. Where these notes and MCP differ, MCP wins.*

## What §11.3 relies on

- **Streamable HTTP, one endpoint.** The server has one MCP endpoint that accepts `POST`. Every JSON-RPC 2.0 request or notification is its own `POST`; the body is a single message. The client sends `Accept: application/json, text/event-stream`, and a request is answered with either one JSON object or a short SSE stream ending in the response.
- **Notifications.** A notification `POST` that the server accepts is answered `202 Accepted` with no body.
- **Request headers.** Every `POST` carries `MCP-Protocol-Version` (for this revision, `2026-07-28`), which must match the version the request names in its `_meta`, and the routing headers `Mcp-Method` and `Mcp-Name`. A server that doesn't support the requested version answers `400` with an `UnsupportedProtocolVersion` error listing what it supports.
- **No handshake, no sessions.** Revision 2026-07-28 removed the `initialize` / `notifications/initialized` handshake and the `Mcp-Session-Id` header. Each request carries its protocol version, client capabilities and client info in `params._meta`. `server/discover` (which servers implement) tells a client the supported versions and capabilities; calling it is optional.
- **Tools.** `tools/list` lists tools (`name`, `description`, `inputSchema`, any JSON Schema 2020-12); `tools/call` has `params: {name, arguments}` and a result with `content` and optional `isError`. Results carry `resultType` (`"complete"` for an ordinary result); list results carry `ttlMs` and `cacheScope`.
- **Errors.** A tool's own failure is a result with `isError: true`. A refusal is a JSON-RPC error.

## How §11.3 maps onto it

- The `Shokai-Act` and `Shokai-Seat` headers ride alongside MCP's own headers on the `tools/call` `POST`. The act's `tool` equals `params.name` (and `Mcp-Name`), and its `arguments` equal `params.arguments` by digest.
- **Open methods.** §11.3 lists the methods a place answers without a seat. Under 2026-07-28 these are `server/discover` and the listing methods. `initialize`, `ping` and `notifications/initialized` exist only in earlier revisions; a place that also serves earlier revisions answers them without a seat too. The reference gate (`@kigenka/shokai/mcp`) does both.
- **Sessions.** "An MCP session is not a seat" applies to earlier revisions, which had `Mcp-Session-Id`. Under 2026-07-28 there are no sessions, and every call carries its act anyway.
- **Refusals.** §11.3 answers a refused call with HTTP `200` and JSON-RPC error `-32040` with `data.shokai`.

## Known tensions (recorded, not changed in v0.3.0)

1. **The refusal code is inside MCP's reserved range.** MCP 2026-07-28 reserves JSON-RPC server-error codes `-32020` to `-32099` for the MCP specification; `-32040` falls inside it. Changing the code is a wire change, so it is listed in SPEC §13 for the editors and left as is in v0.3.0.
2. **The reference tooling still speaks the earlier handshake.** The SDK's conformance runner probes an MCP endpoint with `initialize` and protocol version `2025-06-18`, and the reference gate serves through the official MCP TypeScript SDK in stateless mode. A server that speaks only 2026-07-28 may refuse `initialize`; the runner then reports the MCP checks as failing to initialize, not the door as non-conformant in its core. Probing with `server/discover` and `_meta` is follow-up work (SPEC §13).
3. **HTTP status for a refusal.** MCP answers some transport errors with `4xx` (version, header mismatch, unknown method). A Shōkai refusal is a protocol answer about the act, not a transport error, so §11.3 keeps `200` with the JSON-RPC error.
