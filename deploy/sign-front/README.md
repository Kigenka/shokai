# The sign.kigenka.com front (relay mode), for the rc4 signing page

*Prepared 2026-10-28. Nothing here deploys anything by itself.*

`site/` is what the Vercel project `kigenka-sign` (in the steward's Vercel team) serves at `sign.kigenka.com`, generated by `node deploy/sign-front/build.mjs`:

- **Between sessions:** an inert page ("No signing session is open") with a one-line test-stage notice, and the full notice at `/about` (SIGNING-PAGE-PLAN.md, "Requirement: tell owners it's a test").
- **During a session:** `api/relay.js` forwards `/p/<token>/*` to the reference signing page (`reference/signing-page/server.mjs`) on the steward's machine. Compared with the October 26 front, it also forwards `/about` and the one-tap batch routes (`/api/batch/options`, `/api/batch/verify`), which the rc4 page needs; anything else stays inert.
- **Headers:** the same as the live front: HSTS, `X-Frame-Options: DENY`, CSP `default-src 'none'` with `'self'` scripts and `frame-ancestors 'none'`, `no-store`, `noindex`, `no-referrer`.

`node deploy/sign-front/test.mjs` checks it on loopback against the rc4 page (run by `tools/run-all-suites.sh`).

## Redeploy the inert front (production, no domain or DNS change)

Run by the steward, with YSY's OK. From the repository root, at the commit whose suites passed:

```bash
node deploy/sign-front/build.mjs --check && node deploy/sign-front/test.mjs && node reference/signing-page/test/e2e.mjs
cd deploy/sign-front/site
vercel link --yes --project kigenka-sign --scope <team>    # writes .vercel/ here (git-ignored)
vercel project inspect kigenka-sign --scope <team>          # confirm the team and the domain sign.kigenka.com
vercel deploy --prod --yes --scope <team>                   # production; sign.kigenka.com moves to it by itself
```

Never run `vercel domains`, `vercel alias`, `vercel dns` or `vercel env` for this project: the domain is already the project's production domain, and the front needs no environment variables. `api/_session.js` must say `SESSION = null` in what you deploy (`build.mjs --check` fails otherwise).

Before deploying, write down the current production deployment, the rollback target.

## Smoke check after the deploy

```bash
curl -sSI https://sign.kigenka.com/ | grep -iE '^HTTP|strict-transport|x-frame|content-security|x-robots|cache-control'
curl -sS https://sign.kigenka.com/ | grep -c 'No signing session is open'                    # 1
curl -sS https://sign.kigenka.com/ | grep -c 'test-stage convenience'                        # 1
curl -sS https://sign.kigenka.com/about | grep -cE 'About this signing page|days in advance\. A way'   # 2
R=$(node -e 'process.stdout.write(require("crypto").randomBytes(24).toString("base64url"))')
curl -sS -o /dev/null -w '%{http_code}\n' "https://sign.kigenka.com/p/$R/api/state"           # 404 (inert)
curl -sS -o /dev/null -w '%{http_code}\n' -X POST "https://sign.kigenka.com/p/$R/api/batch/options"   # 404 (inert)
```

The item summaries (every signed field shown, mixed kinds refused, money items on their own tap) appear only inside a session, so production can't show them until the next session. They are checked locally through this same relay code (`test.mjs`) and by the signing page e2e.

## The next session (a separate OK)

A session runs the rc4 reference page, not the October 26 session server: `reference/signing-page/server.mjs` with `RP_ID=sign.kigenka.com NOTICE=test-stage NOTICE_DAYS=90 TOKEN=… RELAY_SECRET=… PORT=8797 TTL_MIN=30 DATA_DIR=… ITEMS=…`, a short-lived tunnel to it, and a copy of `site/` (never `site/` itself) whose `api/_session.js` holds the backend origin, the token's SHA-256, the relay secret and the expiry, deployed to production; afterwards redeploy `site/` (inert). To reuse the owner's existing passkey, copy only the public `owner-credential.json` (its `rp_id` is `sign.kigenka.com`) into the new `DATA_DIR`. In the session, check on the phone that the notice box shows before "Create my passkey", that a card lists its chat key (`owner_binding.platform_key`) and the full representative key, and that any item with an amount asks for its own tap.

## Roll back

`vercel rollback <previous production deployment id> --scope <team>` (or the dashboard's Instant Rollback). After a rollback, Vercel stops moving the domain to new production deployments until one is promoted (`vercel promote <id> --scope <team>`). Nothing signed depends on the front: signatures verify without it.
