# Shōkai v0.3.0

*Release notes for the GitHub release of tag `v0.3.0`, 2026-10-28. Shōkai, the agent introduction protocol, from Kigenka.*

This is the first release of the 0.3 line: the specification, a TypeScript SDK on npm, a conformance runner and a reference place. It is a released version, not 1.0. Review continues, and changes go into later versions.

## In plain words

A place keeps a door. An agent arrives on someone's behalf and introduces itself with a card its owner signed with a passkey, says why it came, and shows the limits its owner signed. The place answers every arrival: it seats the agent, or gives it a leaflet and a kind "not now" it can recover from. Inside, every act is checked against the seat and the owner's limits, the agent reports home in plain words, and conduct has consequences.

## Try it

```bash
npx @kigenka/shokai demo          # a door and a visitor on your machine, in about two seconds
npm install @kigenka/shokai       # build a door, a gate in front of your MCP server, or a representative
npx shokai-conformance <url>      # check a door against the core
```

Then follow [QUICKSTART.md](https://github.com/Kigenka/shokai/blob/v0.3.0/QUICKSTART.md), from a clean machine to a seated visit and a report home.

## What's in it

- **The core specification** ([SPEC.md](https://github.com/Kigenka/shokai/blob/v0.3.0/SPEC.md)): identity and the signed envelope, the door and the leaflet, self-introduction and optional vouches, mandates and limits, the decision, seats and acts, reports home, conduct, the HTTP and MCP bindings, passkey signatures and test vectors. Every MUST and SHOULD is tied to a scenario, a golden trace or a conformance check.
- **Eleven optional extensions**: eight stable (Gatherings, Peer meetings, Visit receipts, Revocation status, Door gifts, Seeking, Meaning notes, Profiles and evidence) and three experimental.
- **`@kigenka/shokai` 0.3.0** on npm: doors, representatives, owner helpers, an MCP gate, `shokai demo` and the conformance runner `shokai-conformance`.
- **Reference implementations**: a place server, a prototype, and a passkey signing page you can run on your own domain ([SIGNING.md](https://github.com/Kigenka/shokai/blob/v0.3.0/SIGNING.md)).

## Compatibility

The wire tag is `shokai/0.3`. Nothing on the wire changed from 0.3.0-rc4, so a peer that names "0.3.0-rc4" in `spec_ref.version` speaks this text, and the conformance runner accepts it with a note (SPEC §3.1). Release candidates rc1 to rc3 lack later additions of the 0.3 line (§2.6, §2.8, §3.6, §7.2). The full list of changes is in the [CHANGELOG](https://github.com/Kigenka/shokai/blob/v0.3.0/CHANGELOG.md#v030-2026-10-28).

## How it was tested

Every suite passes on Node.js 20, 22 and 24: the reference's vectors, golden traces and scenarios, the core conformance checks, the SDK, the signing page end to end, and the quickstart run exactly as written. Outside agents (Hermes Agent, OpenClaw, Muse and Grok Bot) were seated at fictional test places, and the author signed real cards with his own passkey. What we tested, what broke and what we changed: [Field tests](https://github.com/Kigenka/shokai/blob/main/docs/field-tests.md) and [Review history](https://github.com/Kigenka/shokai/blob/main/docs/review-history.md).

## Known limits

- **No outside implementation or review yet.** All testing so far was done inside the project. This is the most useful thing you can help with.
- **Shōkai makes deception costly and traceable, not impossible.** The accepted risks are in the [threat model](https://github.com/Kigenka/shokai/blob/v0.3.0/THREAT-MODEL.md), and the open questions in SPEC §13.
- **No public demo door yet**, and `sign.kigenka.com` opens only for guided signing sessions, with no uptime promise. The reference signing page lets anyone run their own.
- **PATENTS.md is a draft**, pending legal review.
