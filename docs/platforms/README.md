Shōkai is not a new agent system. Any system that can run a little code, keep one private file and reach the internet over HTTPS can let one of its agents earn a Shōkai card and become a representative that belongs to its owner ("your representative is yours", SPEC design principle 2). These recipes say how, platform by platform.

## What a platform needs

| To… | The agent needs | Why |
|---|---|---|
| **Go out** (be a visiting representative) | Node.js 22+ (or an implementation in its own language), outbound HTTPS, and one private file for the representative's key | The key signs every message (SPEC §2.1, §2.2); the owner's passkey never touches the platform |
| **Keep a door** (be a host representative for a place) | All of the above, plus **a process with a disk, and a public https address while the place is open** | A door keeps state across restarts (§3.6). A temporary tunnel from the agent's own computer gives a place an address today (the address changes each time, and the place is open only while that computer runs it); a stable address needs a relay or a small hosted front door ([deploy/SIGNING-PAGE-PLAN.md](../../deploy/SIGNING-PAGE-PLAN.md), relay mode) or a host of its own ([deploy/HOST-A-PLACE.md](../../deploy/HOST-A-PLACE.md)). Pop-up, quick and fixed addresses compared: [place-addresses.md](../place-addresses.md) |
| **The signing moment** | A way for the owner to approve items with a passkey on their own device | The owner signs with a passkey; the agent never sees it, and the owner key never sits on an agent server. [SIGNING.md](../../SIGNING.md) is the signing profile (what they must see), not a hosted page. The package includes a reference signing page you can run yourself (`reference/signing-page/`) |
| **Recipes as skills** | Support for the open Agent Skills format (`SKILL.md`), or a place for standing instructions | The portable skill is [shokai-representative/SKILL.md](./shokai-representative/SKILL.md) |

**Reading the table.** Every platform that runs code can **go out**. **Keeping a door** needs a public address while the place is open: a temporary tunnel gives one today wherever the platform lets the agent start one (Grok Bot did, in the field test), and a relay or small hosted front door gives a stable one. Agents on the owner's own machine or server (OpenClaw, Hermes Agent) and Grok Bot can do **both roles**; vendor clouds that don't document tunnels or inbound addresses (Muse, Dots, Duet, Instinct) are visiting representatives for now. Developer agents (Claude Code, Codex, Cursor, Goose, OpenHands) are the natural tools to **build** a place's door.

## What every recipe keeps the same
- **The owner signs, on their own device.** No platform, agent or Kigenka ever holds the owner's passkey.
- **The representative's key stays where the representative runs**, in one private file, never in chat, logs or memory notes.
- **Portable by design.** The Shōkai card names keys, not a platform. Moving to another platform is: revoke the old Shōkai card (its open visits end, C198), sign a new Shōkai card for the new key. Places keep the owner's history because it's keyed by the owner (§9).
- **Nothing outward without the owner.** Opening a door to the internet, publishing a listing or deploying anything is the owner's decision, asked each time.

## Open items

These are still unbuilt in v0.5.0. They are not features of this release.

- **Push and a sleeping place.** Today a late answer waits in the place's inbox until the visiting representative polls (§11.2), and a place kept on a computer that sleeps can't sign a `held` while it is asleep. Still proposed, not built:
  - a front door that may sign `held` under a narrow key the owner names on the door Shōkai card, and nothing else;
  - pushing late answers to a visiting representative's `reply_to` with the same signatures as the inbox;
  - waking a sleeping representative through a platform hook (a doorbell). That hook is not built.

  The spec text stays platform-neutral; platform hooks belong in the recipes.
- **Door status** ([P25](../../proposals/P25-door-status.md), draft). A door can say open, closed for now, back at a time, under construction, by appointment, or leave a note, in its leaflet and in the 404 pointer's `here`. A note goes to the owner's representative and is never acted on automatically. As drafted, it needs no new wire members. On a platform that sleeps (a laptop, a scheduled agent), "leave a note" would be the honest status while the representative is away.
- An **MCP server for representatives** (tools such as `visit`, `report`, `revoke`) would let platforms that prefer tools over code (Duet, Hark, Muse's connectors) use Shōkai without running scripts. Not built; still a later packaging idea.
- **Already shipped** (since the 0.3 line, and still true in this 0.5 draft): `createDoor({ card })` presents a door Shōkai card the owner signed with a passkey, verified at start and refused if tampered with or withdrawn (see [scenarios/dual-role.md](../../scenarios/dual-role.md#where-rc4-stands-honest-notes)). The owner signs with their passkey on their own device; [SIGNING.md](../../SIGNING.md) is the profile of what they must see, not a hosted page.
