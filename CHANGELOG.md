## v0.5.1, 2026-11-11

A patch release of the package. The specification stays v0.5.0 on the wire: the wire tag is still `shokai/0.5`, `spec_ref.version` is still `"0.5.0"`, and the v0.5.0 JSON Schema file is unchanged. The new members are in a new schema file, `schema/v0.5.1/schema.json`, with its own `$id`. 0.5.1 adds two optional members and one MUST-level rule, so a 0.5.0 peer and a 0.5.1 peer keep talking to each other. What a 0.5.0 peer sees differently is listed under each item.

- **A binding `never` says when it lifts and where to appeal (red-team round 3, V05-F7-04; C288, SPEC-DETAIL §9.3).** A door's `never` reply that binds a key or principal now carries `retry: { kind: "never", until, appeal: { url, place } }`, with `until` at most 180 days after the binding. New door option `appealUrl` (default: the door's inbox address). The new JSON Schema file `schema/v0.5.1/schema.json` (`$id` `https://github.com/Kigenka/shokai/blob/v0.5.1/schema/v0.5.1/schema.json`) adds the two optional members to `Retry` and a `NeverAppeal` definition; `schema/v0.5.0/schema.json` stays byte for byte as released. A 0.5.0 receiver ignores the two members, as the Conventions require of unknown members. A validator that uses the 0.5.0 schema rejects a `never` that carries `until` and `appeal`; to accept them, validate with the 0.5.1 schema file. The package's `@kigenka/shokai/schema.json` is now the 0.5.1 file. The 0.5.1 schema also makes `in_reply_to` optional on `invitation_response`, so the lobby's answer to plain prose or a malformed message validates: SPEC-DETAIL §2.3 says that answer MUST NOT carry `in_reply_to`, and the 0.5.0 schema wrongly required it. Every other `invitation_response` still MUST carry it; a schema can't express that condition.
- **A pasted session is refused (red-team round 3, V05-F10-04; C210).** The credential names add `session_token`, `session_key`, `set_cookie` and `auth_token`, and a pasted `session` object carrying a cookie, token, secret or sid, or a `cookie` holding `name=value`, is refused `CREDENTIAL_NOT_ACCEPTED`. Ordinary words such as a cookie flavor or a booked class session are not.
- **Context questions must not ask for a password, a recovery phrase or seed, or a card number (V05-F10-03; SPEC-DETAIL §6.12, C263, C267; MUST).** A door refuses to start with such context requirements and will not emit them; a visiting representative refuses a request that arrives with them and says so in its report. A 0.5.0 door that asks such a question gets refused by a 0.5.1 representative.
- **"Pass" in human-readable text.** The SDK's report home, its MCP refusal messages, the CLI and the door's English courtesy lines now say *pass* where 0.5.0 said *seat* ("the place no longer knew my pass", "get a pass first", "Your pass is ready"). The wire field `seat` and reason codes such as `SEAT_SCOPE_EXCEEDED` are unchanged. If you matched 0.5.0's message text, match the `reason_code` instead.
- **The specification copies in the package** carry the editor byline "YSY", the pass/`seat` headings and the updated threat model; outdated wording and internal notes were removed.
- **Release tooling.** `tools/schema/schema.mjs` writes the schema named by `release-status.json`'s `schema_version` and fails if a released schema file changes. `tools/check-links-versions.mjs` accepts a package patch version on the specification's major.minor line (`release-status.json` gains `spec_version`), and `tools/verify-quickstart.sh` reads the pinned version from the package.

0.5.0 lacks all of the above. Use 0.5.1.

**In plain English: what changed since v0.3.0.** v0.5.0 brings together the unreleased v0.4.0 work, the v0.5.0 core and what we learned building demo 2.

- **Two kinds of Shōkai card.** A Shōkai visitor card says who a representative agent is here for, why it came and what it may do; a Shōkai host card says who owns a place and what its host representative may do there. Both are signed by their owner with a passkey (from v0.4.0).
- **Spending stays in the owner's hands.** A purchase above the signed limit is held, not refused or slipped through, and the owner can raise the limit for that one purchase with one tap. An owner-signed errand budget sits beside the spending cap, and no card number or account number ever travels in a message (v0.4.0 and v0.5.0).
- **A place says its rules before you walk in.** Conduct rules, a short house summary, which outside services see visitor content, and how long the place keeps records are all signed by the owner and shown before a visitor is admitted. Visitors can ask for their records to be deleted.
- **Trust a place can price.** A place can see a visitor's standing and history in a form it can act on, and a friend can introduce a visitor with a Shōkai introduction card.
- **Host representatives have guards.** Fast checks by code first, a slower judgment second, and nothing a place serves is ever treated as an instruction to the visitor.
- **A door belongs to its website.** A Shōkai host card can name its site, and the site lists its door. A visiting representative won't call a door "the door of" a site unless both agree, so a lookalike door is refused before anything is sent (§3.1.1, from P26 amendment A).
- **Outside the setup goes to the owner.** A host representative handles what its owner signed. Anything else gets "I can't do that yet. I'll check with the owner." The owner sees what was asked for and why, then answers once, adds it to the setup with a new signature, or declines. A visitor's words can never change the setup (§7.5, §7.6, from P32).
- **Reservations.** A place can take bookings within limits the owner signed (time window, time zone, party size), checked by code on both sides, and the host representative signs each booking confirmation (§7.4).
- **Proof it holds up.** An enforcement suite runs a real door on this computer and attacks it (altered, expired, revoked and replayed Shōkai visitor cards, over-limit acts, lookalike doors, outside-the-setup asks); demo 2 runs end to end with no model.
- **Wire tag `shokai/0.5`.** Places keep accepting `shokai/0.3` for 90 days after release.
- **Still open, as post-demo work:** keeping a changed setup across a door restart (SPEC §13 item 30), reservation holds for slots the owner didn't pre-approve (item 31), and the item and reason on a purchase held for the visitor's own owner (item 32).

**P32 is adopted** into this core as §7.4–7.6, provisional, like P27, P28, P31 §2.9 and P26 amendment A, until the open discussion GOVERNANCE.md asks for.

**Specification (SPEC.md).**
- **Two Shōkai cards (§2.3).** A Shōkai card states its `kind`: a **Shōkai visitor card** for going out, a **Shōkai host card** for keeping one place. A Shōkai host card is bound to one place (`place`: principal and entry), carries `host_scope` (actions and duties), `house_digest` (the digest of the house config the owner signed) and `shown_to_owner` (the summary the owner read); an organization's Shōkai host card is signed by the organization's key and carries `org_approval`, the record of the person who approved it. A representative's two Shōkai cards should use separate keys. A Shōkai card without `kind` is read as before (C214).
- **The wrong-kind refusal (§2.4 step 5, C202, trace K1).** A Shōkai host card shown as a visitor's credential gets one fixed, fixable answer: `not_now` / `CREDENTIAL_REQUIRED`, readiness `card_kind`, with the fixed sentence for the owner; never `never`, nothing recorded.
- **The visitor checks who keeps the door (§3.1, §2.6; C203–C207, traces K2–K4).** A visitor doesn't go in, and reports a fixed sentence home, when the place shows a Shōkai visitor card, a Shōkai host card for another place, a Shōkai host card over another house config than the listing names (`house_digest` on listing entries), or a withdrawn Shōkai host card; a withdrawal list it can't fetch ends a spending visit (fail closed). A door whose own Shōkai host card doesn't fit (another place, a changed house) answers nothing until its owner signs a new one.
- **The purchase-only live owner prompt (§1, §5.2, new §7.3, §8.1; C212, C213, trace K5).** The one live owner prompt allowed: a representative may ask a place to hold a purchase (`act.hold_for_owner`) for its owner's passkey `approve_purchase` (new `act_held` and `act_confirmation` messages, reason codes `LIVE_PROMPT_PURCHASE_ONLY` and `HOLD_LAPSED`). Only for an act that spends; disclosed on the Shōkai visitor card (`owner_prompts: "purchase_only"`) and to the place's owner (the `hold_purchases` duty and `purchase_hold_s`); at most 15 minutes; silence is no.
- **An amount carries nothing to pay with (§5.1, C211).** A mandate's `max_amount` authorizes spending; a mandate carrying a payment token or other instrument is `MANDATE_INVALID`.
- **Institutions (new §5.4; C208–C210, trace K6).** Actions marked `requires_customer_link` are served only under a `CustomerLink` the institution made in its own app (co-signed by its key and the owner's passkey, at most 400 days), named in the owner's mandate. Every link failure gets one uniform answer (`CREDENTIAL_REQUIRED`, readiness `customer_link`), so the door is no oracle for who is a customer. A link never widens a mandate, ending it ends its seats, and no money moves before its `money_from` (cooling-off). The credential rule: a representative never holds a password, one-time code, session, account or payment card number; an act carrying one is refused (`CREDENTIAL_NOT_ACCEPTED`).
- **No Shōkai host card, no admission (§2.3, C215, reference scenario K7).** Stated plainly: a door admits no visiting representative unless it holds an active Shōkai host card for that place, and otherwise answers nothing (`503`). The reference door now also closes when its own Shōkai host card has expired or been withdrawn (previously: another place, a changed house or a Shōkai visitor card). An informative note adds that the host representative stands behind the deterministic checks and never replaces them.
- **§12.1** gains the credential and "check who keeps the door" rules; **§13 item 28** lists what v0.4.0 leaves open. `spec_ref` is `{version: "0.4.0"}`; the conformance runner accepts `"0.3.0"` with a note.

- The specification is a small **core** plus eleven optional **extensions** (Gatherings, Peer meetings, Teaching visits, Profiles and evidence, Seeking, Visit receipts, Door gifts, Signed place listings, Revocation status, Meaning notes, W3C VC mapping), each with its own conformance level.

**Specification**

- Declared data asks: each action in a place's listing SHOULD say what personal data it will ask for (`data_asks`, §3.1, check C172).
- A lobby's `visit_receipt` is optional.
- Lobby templates and the sincere-approach heuristics are informative (Appendix C).
- Inbound-door defaults decided: reputation stays local, brands learn only the outcome code, paid introductions get no extra priority, no shared track records, hidden text is shown behind a visible marker, and reason categories are given except for reported declines (§13 item 19).
- Security considerations (§12) are backed by a STRIDE [threat model](./THREAT-MODEL.md).

**New**

- `@kigenka/shokai`, the TypeScript SDK: signed cards, mandates, vouches and envelopes; doors and representatives; visit reports; and `@kigenka/shokai/mcp`, a gate that puts a Shōkai door in front of any MCP server.
- `shokai-conformance`, a conformance runner for any door: core HTTP checks tagged by scenario, opt-in extension checks and the test vectors.
- [QUICKSTART.md](./QUICKSTART.md): a door and a visit in about five minutes.
- Contributor documents: CONTRIBUTING (DCO), GOVERNANCE, SECURITY, CODE_OF_CONDUCT; CI for every suite and the quickstart.

**Tested**

- 814 conformance and scenario checks across the reference place server, the narrated prototype and the HTTP binding pass (2 deferred checks are skipped); every normative statement is traced to a scenario, a golden trace or a check.
- Two red-team rounds: 72 of 72 and 44 of 47 attacks held. The three that don't are browsing by many agents or owners, which stays open by design (see the threat model).
